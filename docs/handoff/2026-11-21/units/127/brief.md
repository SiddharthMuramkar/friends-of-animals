## Acceptance checks (seam)
1. **Register → private** (S1). `as(member).registerListing(valid)` → `{ listingId, slug }`, status `pending_verification`, one `directory.listing_submitted` outbox row and one audit row (`directory.listing_registered`). `getPublicListing({ slug })` → `not_found` for pending, rejected, suspended and withdrawn; `getMyListing()` shows it with every field. A visitor is refused. Invalid input (bad pin, empty services, unknown type, bad phone) → per-field errors, no row.
2. **Encrypted at rest** (S1, raw SQL). `select address, contact_phone from directory_listing` holds neither plaintext; `getMyListing` and `getListingForReview` read both back.
3. **Verify grants the scoped role** (S1). `as(staffAdmin).verifyListing({ listingId, reason })` → `verified`, `status_changed_by/at` from the clock; the owner now passes `updateListing` on this listing and holds `organisation_representative @ organisation:<listingId>` (`listUserRoles`). Reinstating later does not grant twice.
4. **Reason required + audited** (S1). verify/reject/suspend/reinstate with `""`, whitespace or > 1000 chars → `reason_required`/`reason_too_long`, nothing written. With a reason: exactly one `audit_log` row each (`directory.listing_<outcome>`, `entity {type:"directory_listing", id}`, before/after `{status, reason}`, no address/phone).
5. **Transition table** (unit, done: `listing-status.test.ts`, 5 statuses × 7 actions = 35 pairs) + S1: one refused pair (`rejected` + `verify`) → `transition_not_allowed`, nothing written.
6. **Own listing only** (S1). Representative of A calling `updateListing` / `uploadListingDocument` on B → `forbidden` (scope mismatch); member → `forbidden`; staff admin → `forbidden` (staff don't edit content). Owner may edit while `pending_verification` (no role yet); after verification only the role counts (revoked rep → `forbidden` even though still `owner_user_id`).
7. **Edit policy** (S1 + unit, done: `listing-edit.test.ts`). On a verified listing, detail edits (description, services, contact, address, website, public fields) go live at once and write one audit row naming the changed fields (names only); a `name` or `type` change sends it back to `pending_verification` (outcome `resubmitted`, hidden publicly, `directory.listing_submitted` again). Suspended/rejected/withdrawn → `listing_not_editable`. No change → `{ changed: false }`, no row.
8. **Documents staff-only** (S1). Owner/rep uploads (`requestUpload({purpose:"directory_document"})` → `completeUpload` → `uploadListingDocument({listingId, fileId, kind})`); `getListingDocumentUrl` (and Files' generic `getFileDownloadUrl` for that file) → staff admin and super admin get a URL (non-owner staff read audited by Files); the owner, the representative, another member and a visitor → `forbidden`. A file owned by someone else or with another purpose → `invalid_file`.
9. **Public read model** (S1 + unit, done: `public-listing.test.ts`). `getPublicListing` for a verified listing returns name, type, services, description, city, state, pin code and only the contact fields in `public_contact_fields`; never address, owner id, documents, reasons or non-chosen contacts (assert on the JSON string).
10. **Outcome messages** (S1). After verify, reject, suspend and reinstate, `h.drain()` delivers one email + one inbox item to the owner naming the outcome and the reason.
11. **Staff queue** (S1). `listListingsForReview({ status? })` oldest-pending first, keyset pages; `getListingForReview` shows decrypted contacts, documents (kind, status, uploaded at) and the expected-documents checklist for the type.
12. **Authorization per use case** (S1, table). Staff use cases: `staff_admin` and `super_admin` pass; `community_manager`, `member`, the listing's own representative fail `forbidden`, nothing written. `registerListing`/`getMyListing`: user passes, visitor fails. `getPublicListing`: anyone.
13. **Inventory** (unit, #114's coverage test). ## Design (codebase-design; tournament rule, compared in context)
- **(a) Single `directory_listing` aggregate (chosen).** The listing *is* the organisation: scope `{ type: "organisation", id: listing.id }` for `organisation_representative`, `adoption_listing.directory_listing_id` (#129) and `adoption_coordinator @ organisation` (#130) all point at it. Deletion test: an `organisation` table today would hold only id + name copied from the listing, and nothing in M6–M8 reads it apart from the listing. One aggregate, one status, one place to check "is this organisation verified".
- **(b) `organisation` entity + `directory_listing` projection.** Lets one organisation have several listings or none, but no ticket asks for that; every read gains a join and the status question splits across two rows (is the org or the listing suspended?). Reversible later: create `organisation` rows reusing listing ids, so existing grants stay valid. Rejected for now.
- **Status logic: one deep pure function** `decideListingStatus({ from, action, reason, actor })` holds the table (allowed moves, outcome, event, `grantsRepresentative`, reason rules). Use cases are thin: `authorize` → `select … for update` → decide → update + grant + audit + emit in one transaction. Four staff use cases (the ticket's names) share one internal `decideListing(ctx, action, input)`.
- **Edits (the uncertainty-2 choice, in the table):** detail edits on a verified listing are live and audited; identity edits (`name`, `type`) return it to `pending_verification` (action `edit_identity`, outcome `resubmitted`). Verification vouches for who the organisation is; the rest is the organisation's own information. Pending listings stay editable by the owner (no role yet); suspended, rejected and withdrawn are not editable. Pure `classifyListingEdit(before, after)`.
- **Authority:** `listingEditResource(listing)` passes `ownerId` only while pending, so after verification the role is the only authority (revocation bites). Suspension keeps the role; the status rule blocks edits.
- **Documents:** staff-only is a property of the file purpose, enforced in Files' one delivery gate, so neither `/api/files/[id]` nor a module URL can leak them. No original filename stored (63a).
- **Contact privacy (HR-61 default):** public contact = explicit per-field opt-in (`public_contact_fields ⊆ {phone, email, website}`) for every type; address never public, only city, state and pin code. Phone must be an Indian mobile (#58's parser) for now.
- **Slug:** `listingSlugBase(name)` (ASCII-folded, ≤ 60 chars) + `-2`, `-3`… on unique-violation retry in a savepoint (73's pattern). Slug never changes after creation (stable public URL); a name change keeps it.
