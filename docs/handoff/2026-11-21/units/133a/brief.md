## Acceptance criteria as testable checks
1. **Award at close** (S1, drain). Lot closes with top bid ≥ reserve → lot `awaiting_payment`; one `open` offer for the top bidder at their bid, `expires_at` = close + `auctions.paymentWindowHours`; `auction.payment_offered`; after drain the winner has one email + inbox item with the pay link and the IST deadline. Top bid < reserve, or no bids → #131's unsold path (artwork restored), no offer.
2. **Exactly one posting** (S1). Webhook simulator `payment.captured` on the offer's order → batch `captured`, offer `paid`, lot `sold`, `auction.lot_sold`; after drain exactly one `ledger_posting` (`source_type = auction_capture`, `source_id` = gateway payment id), Σdebit = Σcredit = amount (trial balance + raw SUM). Share 0 → 2 lines: Dr 1100 / Cr 4300.
3. **Creator share follows the policy** (pure + S1). Policy 2,500 bps, amount 100 101 paise → Cr `2200 creator_share_payable` 25 025, Cr `4300 auction_proceeds` 75 076 (share = floor(amount × bps / 10 000), remainder to FOA). The bps is snapshotted on the offer at award: changing the policy afterwards doesn't change the posting. Pure property: share + FOA = amount for every amount and bps.
4. **Replay changes nothing** (S1). Same webhook twice → second `duplicate`; Checkout return after the webhook, and a re-emitted capture event drained again → no second posting; offer, lot, batch, audit and outbox rows identical (snapshot before/after).
5. **Expiry → next bidder** (S1, fake clock). Drain before `expires_at` → nothing. Advance past it, drain → offer `expired`, its batch `cancelled` (supersede), defaulter gets `auction.payment_offer_expired`; the next *distinct* bidder whose own highest bid ≥ reserve (defaulter's other bids skipped; ties by earlier `placed_at`) gets an `open` offer at their own highest bid with a fresh window. The job first syncs the batch from the gateway: a capture already on the order at expiry is applied (sold), not expired.
6. **Relist** (S1). No eligible next bidder, or `auctions.maxPaymentOffers` offers already made → lot `relisted`, artwork back to its pre-listing status (each of verified, on_exhibition, retained), `auction.lot_relisted`. A relisted artwork passes #131's `createLot` eligibility again.
7. **Late capture → review, no refund** (S1). Capture on an expired or superseded offer's order → batch `needs_review` with one #79 review case (`not_payable`), offer and lot unchanged, no posting, fake gateway records no refund call. Replaying it adds no second case.
8. **Amount mismatch** (S1). Captured ≠ offer amount → nothing applied, review case `amount_mismatch`, lot stays `awaiting_payment`.
9. **Locked period** (S1, 109a). Capture month locked → the posting lands in the earliest open month, `late_adjustment = true`, `original_period_month` = capture month. The capture itself is never refused.
10. **Consent withdrawn while awaiting payment** (S1). `consent.withdrawn` (auction) → lot `cancelled`, open offer `superseded`, batch `cancelled`, artwork restored; a later capture follows AC 7.
11. **Authorization, every new use case** (S1). `startAuctionPayment`/`getPaymentOffer`: the offer's bidder allowed; another bidder → `not_found`; visitor `forbidden`; auction_manager `forbidden` (staff never pay as the buyer). `getLotPayment`: auction_manager allowed; competition_manager and member `forbidden`. `setAuctionProceedsPolicy`: finance and super_admin allowed (audit row, step-up per #60's money rule); auction_manager, competition_manager, member `forbidden`. Consumers (`awardClosedLot`, `expirePaymentOffer`, the purpose handler) accept only the system worker; a user actor fails.
12. **Transition tables** (pure). Offer: open → paid | expired | superseded; nothing leaves a terminal state. Lot rows added to #131's table: closed –award→ awaiting_payment; awaiting_payment –pay→ sold, –reoffer→ awaiting_payment, –relist→ relisted, –withdraw_consent→ cancelled; `relisted` joins the artwork-restoring set; every other pair stays refused (#131's exhaustive test).
13. **Seed** (S1). Preview seed adds an `awaiting_payment` lot with an open offer for a seeded adult bidder (window ends far ahead: previews have no fake clock), a `sold` lot with its posting, a `relisted` lot; twice = same rows.
14. **Journey + axe** (S2, written, **Not run**). `tests/e2e/133-auction-payment.spec.ts`: seeded winner signs in → `/dashboard/bids` → Pay → Razorpay test card (or 77b's fallback adapter, stated) → paid, "delivery pending". `expectRendersAccessibly` light + dark on `/auctions/pay/[offerId]` (open, expired, paid), `/dashboard/bids`, the admin payment panel, `/admin/auctions/proceeds`; no horizontal scroll at 320 px.

## Design (codebase-design; three interfaces compared, chosen = a)
- **(a) Offer entity + payment batch of one, purpose `auction` (chosen).** `startAuctionPayment` opens a batch through 106a's `openPaymentBatch({ purpose: "auction" })` (no items), links it on the offer, and reuses the open order on a second click. Capture stays in 77a's one funnel (`syncBatch`: gateway truth, dedupe, `FOR UPDATE`); for `auction` batches it calls `PAYMENT_PURPOSES.auction.onCaptured(tx, …)`, which locks the lot row, runs pure `decideAuctionCapture`, and writes offer paid + lot sold + `auction.lot_sold` in the same transaction, or returns `not_payable` / `amount_mismatch` / `duplicate` so #79 opens the review case. The offer table is the cascade's memory (who defaulted, which bps applied).
- **(b) Lot-level payment state + a Razorpay Payment Link per offer:** new port methods and a second webhook family (`payment_link.*`) beside Checkout, and no offer history for the cascade. Rejected: wider port, loses history.
- **(c) Generic `Payable` interface implemented by registrations, donations and offers:** deepest on paper, but 106a already rejected a polymorphic payment subject to keep 77a's landed path; a third model would fork Payments. Rejected for consistency.
- **Depth:** `decideAward({ bids, reservePaise, priorOffers, maxOffers })` → `offer | unsold | relist` covers both close and every expiry; `decideOfferTransition`, `decideAuctionCapture`, `splitProceeds`/`auctionCaptureLines` are the other pure pieces. Use cases are lock → decide → write.
- **Expiry job:** at award, `emit(tx, clock, { type: "auction.payment_offer_due", … }, { availableAt: expiresAt })` (#61a one-off). The handler: offer not open → no-op; `syncBatch(batchId)` first (a payer mid-checkout at the deadline isn't failed); still open and `now ≥ expires_at` → expire, supersede the batch, `decideAward` again. Re-runs are no-ops.
- **Ledger:** the capture rule is keyed by batch purpose (106a's pattern), so registration's Dr 1100 / Cr 4100 rule never sees an auction batch; the auction rule reads the offer by batch id for amount + bps snapshot. One posting by construction: #105's unique `(source_type, source_id, posting_kind)`. Fallback if #105's consumer can't dispatch by purpose: post from 133a's own `auction.lot_sold` consumer with the same key.
- **Proceeds policy table, not a competitions column:** deviation from issues-M8 (`competition.auction_creator_share_bps`, H17/X9) so this unit stays off X9 and #70's admin form; still "the competition's proceeds policy", one row per competition, default 0 bps when absent. Reversible (a later migration can move it).
- **Defaults (reversible, HR-66):** window 72 h; max 3 offers (winner + 2); fallback amount = that bidder's own highest bid; relisted = terminal for this lot, artwork released, manager drafts a new lot; no grace beyond the gateway sync; manager can't cancel an `awaiting_payment` lot (consent withdrawal still does).
